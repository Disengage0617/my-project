# 台球厅私域运营小程序第一轮方案

## 1. 项目定位

面向单店/轻连锁台球厅的私域运营小程序，先解决“查空桌、查价格、预约、员工开关台、活动承接、客户沉淀”闭环。

一期不做大而全收银系统，也不做纯营销展示页。核心价值是把顾客预约、桌台状态、员工履约和私域客户数据连起来。

## 1.1 已确认决策

- 一期不收定金，不接支付和退款。
- 商家端一期做小程序内简化后台，不单独做 Web 后台。
- 助教能力纳入一期：支持助教资料、状态展示和预约。
- 活动一期由商家编写上传，用户端支持展示和报名。
- 桌台状态一期采用“用户提交到店 + 员工核实确认 + 员工开关台”方案，不做桌台二维码。
- 营业时间按 24 小时处理，桌台数量按 40 张配置。
- 用户可提前 30 分钟预约；未到店用户禁止预约 3 天，店长可手动解除。

## 2. 目标用户与核心场景

### 顾客

- 到店前查看空桌、价格、营业时间、活动。
- 选择日期、时间、桌型或桌台并提交预约。
- 查看预约状态、取消规则、保留时间和客服入口。

### 员工/助教

- 查看今日预约和待处理请求。
- 确认预约、到店开台、关台、释放超时预约。
- 维护桌台状态：空闲、已预约、使用中、清洁中、维修中、停用。
- 助教切换状态：未上班、空闲、上钟中、休息中、已下班。

### 店长/商家

- 配置门店、桌台、价格、营业时间、预约规则、活动。
- 查看预约记录、客户基础信息、活动参与数据。
- 后续通过公众号、企微、社群等做合规私域触达。

## 3. MVP 范围

### P0 必做

- 微信登录与基础身份识别。
- 首页展示当前空桌数、活动入口、快速预约入口。
- 价格展示：桌型价、时段价、会员价提示、助教价。
- 桌台预约：日期、时间、桌型/桌台、人数、助教需求、备注、规则确认。
- 助教资料、状态展示和预约。
- 活动展示和报名。
- 服务端预约冲突校验，防止同一桌台同一时段重复预约。
- 员工确认预约、开台、关台、超时释放。
- 商家配置门店、桌台、价格、营业时间、活动。
- 客户基础信息和预约记录沉淀。

### P1 增强

- 活动配置与用户端展示强化。
- 预约取消规则与保留时间配置。
- 桌台状态 10-30 秒轮询刷新。
- 基础经营看板。

### 一期暂不做

- 支付、定金、退款。
- 灯控、门禁、收银硬件集成。
- 储值卡、复杂会员卡、优惠券核销。
- 自动化营销群发。
- 多门店财务对账。

## 4. 产品结构

### 用户端小程序

- 首页：门店状态、空桌数、空闲助教数、今日价格、活动、立即预约。
- 门店详情：地址、电话、营业时间、环境图、预约规则、取消规则。
- 价格页：桌型价、时段价、会员价、套餐价、助教价。
- 预约页：选日期、选时间、选桌型/桌台、填人数/助教需求、确认规则。
- 助教页：助教资料、标签、价格、状态、可预约时间。
- 活动页：新人优惠、套餐、赛事、会员活动、活动报名。
- 订单页：待确认、待到店、进行中、已完成、已取消。
- 我的：资料、预约记录、客服、会员入口预留。

### 员工/助教端

- 工作台：今日预约、待确认预约、服务请求、桌台异常。
- 桌台管理：按区域网格展示桌台，支持开台、关台、清洁、维修、换桌。
- 预约处理：确认、取消、改期、到店开台、超时释放。
- 我的：身份切换、上下班状态、权限说明。

### 商家管理端

- 看板：今日预约、当前空桌、桌台利用率、新增客户、活动参与。
- 门店：基础信息、营业时间、预约规则。
- 桌台：编号、桌型、区域、启停、状态。
- 价格：普通价、会员价、时段价、套餐价、助教价。
- 活动：活动类型、时间、名额、规则、上下架。
- 活动报名：报名记录、人数、联系方式、报名状态。
- 客户：客户资料、预约记录、最近到店、标签。
- 触达：服务通知和营销触达记录。

## 5. 关键流程

### 用户预约

看空桌 -> 选日期/时间 -> 选桌型或桌台 -> 补充人数/助教需求 -> 查看价格和规则 -> 提交预约 -> 获得预约结果。

要求预约流程不超过 5 步。提交前必须展示保留时间、取消规则和预计价格。

### 助教预约

查看助教列表 -> 选择助教和服务时间 -> 绑定桌台预约或单独提交助教需求 -> 员工确认 -> 用户获得预约结果。

一期建议先做“助教随桌台预约”，减少单独排班和计费复杂度。

### 活动报名

查看活动 -> 阅读活动规则、时间、名额 -> 填写报名信息 -> 提交报名 -> 商家后台查看报名名单。

一期活动只做展示和报名，不做在线支付、优惠券核销和复杂报名审核。

### 员工履约

查看今日预约 -> 确认预约 -> 用户到店 -> 开台 -> 桌台变为使用中 -> 关台 -> 桌台变为空闲或清洁中。

员工开台、关台、确认预约应尽量 2 步内完成。

### 商家配置

配置门店 -> 配置桌台 -> 配置价格 -> 发布活动 -> 查看预约和客户数据。

首次配置建议按这个顺序做引导。

## 6. 设计规则

- 首页用大数字突出“当前空桌 X 张”“空闲助教 X 位”。
- 主操作突出“立即预约”，预约确认栏固定在底部。
- 桌台管理采用网格卡片，卡片显示编号、桌型、状态、下一预约时间。
- 状态色建议：空闲绿色、已预约蓝色、使用中橙色、清洁中灰色、维修中红色、停用深灰。
- 视觉风格建议年轻、利落、有运动感，主色可用台呢绿，行动色用金色或荧光青。
- 空状态要给下一步：无空桌推荐最近可约时间，无活动引导预约，无订单引导立即预约。
- 预约冲突时推荐相邻时段或同类型桌台。

## 6.1 桌台状态方案

一期采用“用户提交到店 + 员工核实确认 + 员工开关台”方案。

### 一期方案：用户提交到店 + 员工确认

- 用户预约成功后，到店在小程序点击“我已到店”。
- 员工工作台收到待核实提醒。
- 员工核实用户后设置为“已到店”，并执行开台。
- 桌台状态变为“使用中”。
- 关台由员工操作，桌台变为“空闲”或“清洁中”。
- 如果用户未到店，员工标记“未到店”，系统限制该用户 3 天内不可预约。

优点：不需要二维码和硬件，开发成本低，员工仍保留最终核实权。缺点：状态准确性依赖员工核实和开关台动作。

### 后续增强方案：接入现有计费/灯控系统

- 如果门店已有计费或灯控系统，优先对接其开台、关台、计时状态。
- 小程序只读取状态并承接预约，不直接控制硬件。

优点：状态最准，员工负担最低。缺点：对接成本高，依赖厂商接口。

### 暂不推荐方案：摄像头/传感器识别

- 用摄像头、红外、压力、用电检测判断桌台是否有人。

优点：自动化程度高。缺点：成本、误判、隐私和维护复杂度都高，不适合 MVP。

## 7. 后端方案

### 核心数据模型

- `user`：微信身份、昵称、手机号授权、角色。
- `staff_user`：员工、店长、管理员账号和门店权限。
- `store`：门店信息、营业时间、预约规则、取消规则。
- `billiard_table`：桌台编号、桌型、区域、状态、启用状态。
- `table_status_log`：桌台状态流水。
- `price_rule`：桌型价、时段价、会员价、助教价、套餐价。
- `assistant`：助教资料、标签、服务价、状态、可预约时间。
- `assistant_status_log`：助教状态流水。
- `reservation`：预约单、时间段、人数、助教需求、状态。
- `reservation_lock`：短时锁，防并发预约。
- `campaign`：活动名称、类型、时间、规则、库存、上下架。
- `campaign_registration`：活动报名记录、用户、人数、联系方式、报名状态。
- `customer_profile`：客户档案、预约次数、偏好、最近到店。
- `customer_tag`：客户标签。
- `notification_task`：服务通知、营销触达、授权状态、发送结果。
- `audit_log`：后台关键操作审计。

### 核心接口/云函数

- 登录与身份：微信登录、手机号授权、获取当前角色、身份切换。
- 首页：门店概览、空桌数、空闲助教数、推荐活动。
- 门店与价格：门店详情、营业时间、规则、时段价格。
- 桌台：桌台列表、状态查询、可预约时间。
- 预约：创建、锁定、冲突校验、取消、改期、详情、我的预约。
- 员工工作台：今日预约、待确认、确认、开台、关台、超时释放。
- 助教：助教列表、状态查询、助教预约、状态切换。
- 桌台管理：新增、编辑、启停、状态更新、状态流水。
- 活动：列表、详情、新建、编辑、发布、下架、报名、报名名单。
- 客户：列表、详情、预约记录、标签管理。
- 看板：预约数、空桌数、利用率、新增客户、活动参与。

### 权限与风控

- 所有业务表保留 `store_id`，即使 MVP 单门店，也按门店隔离。
- 手机号、消费偏好、触达记录仅店长/管理员可见，普通员工不允许导出。
- 预约创建必须服务端最终校验，同桌同时间建立唯一约束。
- 创建预约时使用短锁，避免并发撞单。
- 桌台状态变更写流水，开台/关台只允许员工及以上角色操作。
- 服务通知和营销触达分开，营销触达必须检查授权。
- 一期不收定金；如果后续加入定金，支付回调必须幂等，订单状态和预约状态分离。

## 8. 运营指标

- 预约转化：首页访问、进入预约、提交预约、预约成功率。
- 桌台效率：当前空桌数、桌台利用率、平均使用时长、清洁/维修占用时长。
- 预约质量：冲突拦截数、取消率、爽约率、超时释放数。
- 客户沉淀：新增客户数、手机号授权数、复购客户数、最近到店时间。
- 员工执行：确认预约耗时、开台/关台次数、状态未更新异常数。
- 活动效果：活动曝光、点击、参与预约数、名额消耗。
- 触达效果：服务通知成功率、营销授权人数、触达后预约数。

## 9. 验收标准

- 用户能完成微信登录。
- 用户能在首页看到当前空桌数。
- 用户能查看桌台价格、营业时间和活动。
- 用户能完成一次完整桌台预约。
- 用户能查看助教资料、状态并提交助教预约需求。
- 用户能查看活动并提交报名。
- 同一桌台同一时间段不能重复预约。
- 用户提交预约前能看到保留时间、预计价格和取消规则。
- 员工能确认预约、开台、关台。
- 员工开台后，桌台状态变为使用中。
- 员工关台后，桌台状态变为空闲或清洁中。
- 商家能配置至少 1 家门店、20 张桌台、基础价格和 1 个活动。
- 商家能在小程序后台编写、发布活动，并查看活动报名名单。
- 商家能查看客户基础信息和预约记录。
- 一期不依赖灯控、收银、支付，也能跑通预约闭环。

## 10. 核心风险与待确认

### 核心风险

- 桌台状态依赖员工人工维护，若执行不到位，用户看到的空桌会失真。
- 高峰期爽约会影响资源利用，一期通过保留时间、超时释放和黑名单/备注机制控制。
- 预约并发必须优先保障，锁和数据库约束是 P0。
- 微信小程序不能承诺无限营销群发，私域触达需要授权和外部渠道承接。
- 助教信息展示涉及隐私、排班和服务边界，需要门店明确规则。

### 待确认问题

- 一期是否必须接入现有收银系统。
- 试点门店桌台数量、助教数量、营业时间和预约规则。
- 助教价格、服务时长和排班规则。
- 活动报名是否默认需要审核。

## 11. 建议推进节奏

- 第 1 周：确认试点门店、业务规则、到店确认流程、页面原型。
- 第 2-3 周：完成用户端预约、员工端开关台、后台基础配置。
- 第 4 周：完成冲突校验、状态流水、活动展示、客户沉淀。
- 第 5 周：门店试跑，修正桌台状态、预约规则、员工操作路径。
- 第 6 周：小范围上线，观察预约成功率、爽约率、员工状态更新率。
