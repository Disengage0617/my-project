# 版本管理与全局复用规则建议

## 1. 项目内版本管理规则

- 每个可交付版本必须创建独立 Git 分支。
- 分支统一使用 `codex/` 前缀。
- 每轮 agent 工作结束后，由 coordinator 统一验收后再提交。
- 禁止多个 agent 同时修改同一文件、同一模块。
- 提交前必须检查 `git status --short`。
- 提交前必须确认临时目录、依赖目录、密钥文件未入库。
- 每次提交信息必须说明本轮产物类型，例如 `docs`、`backend`、`frontend`、`test`、`release`。
- 若配置了远程仓库，每个版本提交后需要推送对应分支。
- 未配置远程仓库时，只能完成本地分支和本地提交，并在汇报中说明未推送原因。

## 3. 建议写入全局 MD 的固定规则

### 多 Agent 调度

- coordinator 负责拆解、分派、合并、复验、阶段验收和风险控制。
- 产品、设计、前端、后端、测试、验收 agent 必须有明确文件/模块边界。
- 只读 agent 不得修改文件。
- worker agent 修改文件前必须说明允许改动范围。
- 多个 worker 不得同时修改同一文件或同一业务模块。
- 每轮结束必须输出：完成内容、变更文件、验证结果、剩余风险。

### Git 版本

- 每个版本必须先建分支再修改。
- 每个阶段性产物必须提交到 Git。
- 提交前必须检查工作区状态。
- 禁止提交 `.env`、密钥、临时下载目录、依赖目录。
- 有远程仓库时，版本分支必须推送。
- 没有远程仓库时，必须明确提示“仅完成本地提交”。

### 文档沉淀

- 业务规则必须写入 `docs/`。
- 状态机、接口协议、页面路由、测试清单必须分文件维护。
- 每次用户拍板的规则要同步到业务规则文档。
- 不确定事项必须进入“待确认”清单，不得擅自假设为最终规则。

## 4. 可复用模块总结

### 产品/协作模块

- 多 Agent 连续执行：中枢拆解、分派、合并、测试、验收、阶段汇报。
- 角色职责边界：产品、设计、前端、后端、测试、验收官分工明确。
- MVP 范围控制：P0/P1/P2、已确认规则、待确认规则、不做范围。
- 预约类业务：资源预约、时间冲突、短锁、状态机、爽约限制、权限校验。
- 权限与审计：用户、员工、店长、管理员分层，敏感字段脱敏，关键操作写日志。
- 验收模板：PRD 覆盖、页面、接口、权限、状态机、异常态、空态、自动化测试。

### 后端模块

- 云函数统一入口：`action + payload` 路由到 handler。
- 标准响应：成功返回 `ok/data`，失败返回 `ok/code/message`。
- `businessError(code, message)` 业务错误标准化。
- 参数兼容层：支持 `camelCase` 入参，服务端内部统一为 `snake_case`。
- 租户/门店隔离：所有业务读写必须带隔离字段。
- 角色权限工具：按最低角色校验接口权限。
- 资源可用性校验：存在、归属、启用、状态可用。
- 时间冲突校验：`new_start < existing_end && new_end > existing_start`。
- 短锁模块：资源抢占使用 30-60 秒 TTL 防撞单。
- 审计日志模块：配置类、状态变更类、权限类操作写审计。
- MVP 初始化与自检：种子数据、初始化校验、smoke test 可复用。

### 前端模块

- `services/api.js`：统一 API 调用、云函数封装、mock fallback、错误文案。
- `utils/constants.js`：集中维护状态枚举、文案、状态色。
- `utils/mock.js`：无云环境时跑页面骨架。
- 全局样式类：`.page`、`.page-header`、`.panel`、`.card`、`.row`、`.grid`、`.stack`、`.button`、`.tag`、`.empty`。
- 页面结构：统一 `pages/name/index.{js,wxml,wxss,json}`。
- 页面状态模式：`loading`、`errorMessage`、`actioning/actioningId`、`submitting`。
- 数据归一化：进入页面前 `normalize`，兼容 `_id/id`、蛇形字段、驼峰字段。
- 空状态模式：不只显示“暂无”，要提供下一步操作。

### 测试模块

- 本地自动化：`npm test`、规则单测、handler 流程测试。
- 假数据库：`createFakeDb`、集合 CRUD mock、查询命令 mock。
- 种子数据：门店、用户、员工、资源、预约、状态日志、审计日志。
- 时间规则：提前量、开始/结束时间合法性、过期限制。
- 权限规则：普通用户、员工、店长、跨门店、禁用员工。
- 资源占用：时间冲突、短锁、维修/停用/不可用资源。
- 状态机回归：创建、到店、核实、开台、关台、完成。
- 风控闭环：爽约、限制、解除、审计。
- 前端验收扫描：JS/JSON 解析、中文乱码、WXML 标签闭合、mock 链路。
- 真实环境烟测：初始化校验、正常闭环、规则拦截、多账号权限。

## 5. 建议写入全局 MD 的条目

### 协作与暂停

- 默认不主动联网，除非用户明确授权。
- 用户说“继续做/开始执行/按方案推进”后，默认连续执行到阶段验收节点。
- 普通错误不暂停：代码报错、测试失败、字段不一致、页面入口缺失、普通 UI 缺陷，由 Codex 自行修复并复验。
- 必须暂停：账号密钥、云环境 ID、真实业务资料、部署、删除/重置、覆盖线上配置、重大业务取舍。
- 复杂项目固定分层：产品、设计、前端、后端、测试、验收。
- 阶段未验收通过前，不讨论上传、提交审核、发布。

### 后端

- 所有业务表必须有租户/门店隔离字段。
- 数据库字段使用 `snake_case`，前端入参可兼容 `camelCase`。
- 状态枚举使用英文 code，中文只做展示映射。
- 所有写接口必须有身份校验、权限校验、参数校验、状态机校验、审计/日志策略。
- 时间冲突统一使用区间重叠公式。
- 高并发资源抢占统一使用短锁或事务。
- 金额统一用分，时间统一用服务端时间/ISO 或 timestamp，同项目必须一致。

### 前端

- 微信小程序页面统一采用 `pages/name/index.{js,wxml,wxss,json}`。
- API 调用必须走 `services/api.js`，页面不得直接写云函数调用。
- 页面状态字段统一命名：`loading`、`errorMessage`、`actioning/actioningId`、`submitting`。
- 列表数据进入页面前先 `normalize`。
- 全局样式优先复用基础类，页面 wxss 只写页面特有选择态或布局微调。
- 状态枚举、状态文案、状态色集中维护。
- 中文文件必须统一 UTF-8 保存。
- 提交/危险操作必须有防重复提交、错误提示、成功反馈和刷新逻辑。

### 测试

- 测试必须先声明验收口径，避免 MVP、阶段版、全量版混验。
- 自动化、手工、多账号、真实环境验收要分层记录。
- 每个业务闭环至少覆盖：成功路径、权限拒绝、资源冲突、状态流转、审计日志。
- 阶段通过不等于最终通过，报告必须写清结论边界。
- 测试报告统一包含：执行 agent、完成内容、验证结果、剩余问题、下一步负责 agent。
- 真实云环境、账号、密钥、部署、重置数据属于暂停项，需用户授权。
- 生产能力与测试辅助接口必须隔离，测试入口不得默认暴露给用户端。
