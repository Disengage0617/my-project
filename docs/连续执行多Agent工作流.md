# 连续执行多 Agent 工作流

## 1. 工作流目标

把协作模式固定为：Codex 作为中枢，默认连续推进；多 agent 自动分工；只有遇到关键问题、阶段结束或外部授权时才停下来问用户。

## 2. 基本原则

- 不在每个小节点停下来等用户发号施令。
- 用户确认方向后，Codex 自动拆解、分派、合并、测试、修复。
- 简单问题直接处理，复杂问题分配给对应 agent。
- 每轮以“阶段性可验收结果”为汇报单位。
- 可自行解决的问题自行解决，不把普通缺陷抛给用户。
- 项目执行由 Codex 中枢 agent 统一指派；每个完整流程必须从第一步推进到验收官完整检核。
- 除非需要用户提供外部信息、业务决策或高风险授权，否则任何 agent 不得中途停止等待用户。
- 在完整产品流程实现、测试工程师回归通过、验收官确认无关键问题前，不讨论上传、提交审核或发布。

## 3. Agent 分工

| agent | 负责内容 |
|---|---|
| Codex 中枢 | 拆解、分派、合并、验收、风险判断 |
| 产品经理 agent | 规则、流程、验收标准 |
| 设计师 agent | 信息架构、低保真、交互状态 |
| 后端工程师 agent | 数据模型、云函数、权限、校验、测试 |
| 前端工程师 agent | 页面、表单、接口接入、交互反馈 |
| QA agent | 测试用例、缺陷复核、回归验收 |
| 验收官 agent | 阶段验收、发布风险 |

## 3.1 固定执行顺序

完整流程固定按以下顺序推进：

1. Codex 中枢：拆解目标、划定边界、分配 agent 和文件范围。
2. 产品经理 agent：核对需求、流程、页面范围、验收标准。
3. 设计师 agent：完成信息架构、页面布局、视觉规范、交互状态。
4. 前端工程师 agent：实现页面、交互、状态刷新、接口接入、错误提示。
5. 后端工程师 agent：实现接口、云函数、数据读写、权限、校验、状态机。
6. QA agent：跑自动化测试、手工验收清单、边界场景、回归验证。
7. 验收官 agent：对照 PRD 和验收标准做完整检核，判断是否可交付。
8. Codex 中枢：合并结论；只有验收官确认无关键问题后，才找用户检查。

## 3.2 跨 Agent 消息格式

中枢分派、agent 状态回传、交接、评审、修复指令，必须使用以下格式：

```text
message_type: instruction / status / handoff / review / fix
request_id: REQ-YYYYMMDD-HHMMSS-简短任务名
from_lane: coordinator / product-planning / research / visual-design / frontend / backend / qa / reviewer / simple-helper
to_lane: 目标 lane
created_at: ISO 时间或当前日期时间
recorded_in: 当前对话 / docs/worklog.md / docs/shared.md / lanes/<lane>/worklog.md

消息内容：
- 背景：
- 任务：
- 输入材料：
- 允许改动范围：
- 禁止改动范围：
- 输出要求：
- 验证方式：
- 暂停条件：
```

未按该格式输出时，视为流程不合规，需要立即重写。

## 3.3 自动回流闭环

固定线程存在时，多 Agent 不再靠用户手动复制提示词推进，而是按以下循环自动跑：

1. 中枢向目标 agent 线程投递 `instruction`。
2. agent 执行当前阶段任务。
3. agent 完成后向 `coordinator` 输出 `handoff` 或 `status`。
4. 中枢读取该线程结果。
5. 中枢合并结论，决定继续给下一 agent 发 `instruction`，或给原 agent/其他 agent 发 `fix`。
6. QA 复验，验收官复核。
7. 直到验收官确认无关键问题，或触发必须找用户的暂停条件。

agent 回传必须包含：

- 完成内容。
- 改动文件。
- 验证结果。
- 剩余问题。
- 建议下一步负责 agent。
- 是否触发暂停条件。

中枢不得要求用户在固定线程之间手动复制提示词；除非当前环境没有可用线程工具。

## 4. 什么时候连续执行

- 用户说“继续做”“开始执行”“按方案推进”。
- 当前任务仍在已确认业务范围内。
- 问题属于代码、文档、测试、字段、页面入口等可自行修复内容。
- 子任务可以通过 agent 并行完成，不需要用户外部信息。

## 5. 什么时候暂停询问

- 需要云开发环境 ID、账号、密钥、部署权限。
- 需要真实门店资料、真实桌台编号、真实价格。
- 需要删除、重置、覆盖线上数据。
- 业务规则冲突，继续做会影响 MVP 范围。
- 阶段性成果已完成，需要用户验收或决定是否进入下一阶段。
- 任务跨层级扩大，建议新开对话框。

## 5.1 不允许暂停的普通问题

以下问题由 Codex 中枢继续指派修复并回归，不暂停找用户：

- 代码报错、语法错误、测试失败。
- 页面乱码、布局错位、按钮不可点、状态不刷新。
- 字段映射不一致、接口入参/出参小范围不一致。
- 文档、接口、页面、测试之间的小范围矛盾。
- 缺少加载中、空状态、失败提示、重复提交保护。
- 普通回归缺陷、普通 UI 细节、普通交互问题。
- 当前流程内需要补测试、补入口、补状态、补错误提示。

## 5.2 验收官完整检核标准

验收官 agent 必须完成以下检查后，Codex 中枢才可以把结果交给用户：

- PRD 范围是否覆盖。
- 页面是否无明显乱码、错位、空白和不可读文案。
- 关键用户流程是否跑通。
- 员工/店长流程是否跑通。
- 后端权限、状态机、冲突校验、数据隔离是否通过测试。
- 自动化测试是否通过。
- 失败态、空态、加载态、重复提交保护是否存在。
- 已知缺陷是否修复并回归。
- 剩余问题是否全部标为非阻塞，且有明确后续计划。

## 6. 每轮输出格式

阶段完成时输出：

- 本轮执行 agent。
- 本轮完成内容。
- 验证结果。
- 剩余问题。
- 下一步任务。
- 下一步负责 agent。
- 是否需要新开对话框。

## 7. 当前项目适用方式

台球厅私域运营小程序后续默认按此模式执行：

- 开发阶段：连续推进代码、测试、文档。
- 联调阶段：遇到云环境 ID 或微信开发者工具授权才暂停。
- 测试阶段：QA 发现普通缺陷后，Codex 直接分派修复并回归。
- 阶段完成：统一汇报结果，不逐小步询问。
