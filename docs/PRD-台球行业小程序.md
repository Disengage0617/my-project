# PRD：台球行业小程序

## 1. Summary

本产品是面向台球馆的微信小程序和商家管理工具。它帮助顾客查看实时空桌、助教状态、价格和活动，并支持提前预约；同时帮助商家管理桌台、活动和私域客户。

## 3. Background

台球馆常见经营问题是：用户到店前不知道有没有空桌，预约主要靠微信或电话，助教状态不透明，活动靠朋友圈和社群传播，客户数据分散在前台、收银系统、微信群和人工记录中。

小程序适合作为低门槛入口。用户不用下载 App，商家可以通过二维码、微信群、公众号、抖音/小红书内容入口承接用户。

竞品和替代方案已经存在，包括美团/点评/抖音团购、小红书种草、传统台球计费系统、微信群预约。但这些方案通常只解决“获客”或“收银计费”的一部分，没有很好连接用户预约、桌台状态、助教状态和私域运营。

## 4. Objective

### 目标

打造一个台球馆可落地使用的预约与私域经营小程序，让用户更快决策，让商家更少靠人工沟通。

### 用户价值

- 用户能看到当前还有几张桌。
- 用户能看到助教是否空闲。
- 用户能提前预约。
- 用户能看到价格和活动。

### 商家价值

- 降低前台咨询压力。
- 提高高峰期桌台调度效率。
- 沉淀客户信息和预约记录。
- 通过活动和触达提高复购。

### 关键结果

- 试点门店 80% 的预约可通过小程序完成。
- 用户完成预约流程不超过 5 步。
- 员工开台/关台操作不超过 2 步。
- 同一桌台同一时段重复预约率为 0。
- MVP 上线后能支持至少 1 家门店、20 张桌台、10 名助教。

## 5. Market Segment(s)

### 主要门店

- 6 张桌以上的台球馆。
- 有高峰排队问题的门店。
- 有助教、陪练、教练服务的门店。
- 有微信群、会员、活动、赛事运营的门店。

### 暂不优先

- 只有少量桌台、完全靠熟客和微信群经营的小店。
- 必须立即接入复杂灯控、收银、门禁的门店。
- 需要多门店总部管理和复杂财务对账的连锁品牌。

## 6. Value Proposition(s)

### 顾客价值

- 少等待：提前知道是否有空桌。
- 少沟通：不用反复问客服价格、时间、助教。
- 更确定：预约成功后有明确状态和规则。
- 更容易参与活动：活动直接在小程序展示。

### 商家价值

- 少人工：减少重复咨询和手工登记。
- 更准：桌台状态、预约状态、助教状态统一管理。
- 有数据：客户基础信息、预约记录、活动参与记录可沉淀。
- 能运营：后续可做会员、优惠券、召回。

### 相比竞品

- 比美团/抖音团购更懂桌台状态和预约冲突。
- 比小红书种草更靠近交易和门店执行。
- 比传统计费系统更重视用户端体验和私域承接。

## 7. Solution

### 7.1 用户流程

#### 用户预约桌台

首页查看空桌数 → 查看价格和活动 → 选择日期/时间 → 选择桌型或桌台 → 提交预约 → 获取预约结果。

#### 用户查看助教

首页查看可预约助教数 → 进入助教列表 → 查看状态、价格、标签 → 选择时间 → 提交预约。

#### 员工处理预约

员工进入工作台 → 查看今日预约 → 用户到店 → 确认开台 → 桌台变为使用中 → 关台后进入空闲或清洁中。

#### 商家配置活动

商家进入后台 → 新建活动 → 设置名称、时间、规则、适用门店 → 发布 → 用户端展示。

#### 商家触达客户

商家查看客户列表 → 按预约记录或标签筛选 → 选择服务提醒或营销触达 → 发送前检查授权和渠道。

### 7.2 页面范围

#### 用户端小程序

- 首页：门店、空桌数、助教空闲数、活动、预约入口。
- 门店详情：地址、营业时间、电话、环境、规则。
- 价格页：桌型、时段价、会员价、助教价。
- 预约页：日期、时间、桌型、人数、助教、备注。
- 订单页：待确认、待到店、进行中、已完成、已取消。
- 活动页：优惠、套餐、赛事、新人活动。
- 我的：个人资料、预约记录、客服、设置。

#### 员工/助教端

- 工作台：今日预约、待处理请求、当前状态。
- 桌台管理：空闲、已预约、使用中、清洁中、维修中。
- 助教状态：未上班、空闲、上钟中、休息中、已下班。
- 服务请求：呼叫助教、清洁、设备问题。

#### 商家管理端

- 看板：首页数据概览。
- 门店管理：门店信息、营业时间。
- 桌台管理：桌台编号、桌型、区域、状态。
- 价格管理：桌费、时段价、会员价、助教价。
- 预约管理：预约列表、确认、取消、改期。
- 活动管理：活动配置和发布。
- 客户管理：客户信息、预约记录、标签。
- 触达管理：预约提醒、活动通知、会员召回。

### 7.3 功能优先级

| 优先级 | 功能 | 说明 |
|---|---|---|
| P0 | 空桌数展示 | 首页展示当前可用桌台数 |
| P0 | 价格展示 | 展示桌型、时段、助教价格 |
| P0 | 桌台预约 | 用户选择时间并提交预约 |
| P0 | 预约冲突校验 | 服务端保证不能重复预约 |
| P0 | 员工开台关台 | 员工更新桌台状态 |
| P0 | 商家配置桌台价格 | 后台配置基础运营数据 |
| P1 | 助教状态 | 展示上钟、空闲、休息等状态 |
| P1 | 活动展示 | 商家配置活动，用户端展示 |
| P1 | 客户信息沉淀 | 查看客户基础信息和预约记录 |
| P1 | 预约提醒 | 微信订阅消息提醒 |
| P2 | 优惠券/会员卡 | 提升复购 |
| P2 | 私域触达 | 活动通知、会员召回 |
| P2 | 数据看板 | 桌台利用率、预约数、客户数 |
| P2 | 收银/灯控集成 | 复杂行业能力，后置 |

### 7.4 状态定义

#### 桌台状态

- 空闲：可预约或开台。
- 已预约：未来时段已被预约。
- 锁定中：用户正在提交预约或支付。
- 使用中：已经开台。
- 清洁中：刚结束使用，暂不可预约。
- 维修中：设备异常。
- 停用：商家下架。

#### 助教状态

- 未上班。
- 空闲。
- 上钟中。
- 休息中。
- 已下班。

#### 预约状态

- 待确认。
- 已预约。
- 待到店。
- 进行中。
- 已完成。
- 已取消。
- 退款中。
- 已退款。

### 7.5 数据对象

- user：用户。
- store：门店。
- billiard_table：桌台。
- table_status_log：桌台状态流水。
- assistant：助教。
- assistant_status_log：助教状态流水。
- reservation：预约。
- order：订单。
- campaign：活动。
- customer_profile：客户档案。
- customer_tag：客户标签。
- notification_task：触达任务。

### 7.6 技术假设

- 一期先不接灯控和收银。
- 桌台状态由员工端维护。
- 小程序端使用轮询刷新状态，10-30 秒可接受。
- 预约创建时由服务端做冲突校验。
- 如涉及定金支付，支付回调必须幂等。
- 客户手机号、消费记录等敏感信息必须做权限控制。

## 8. Release

### MVP

建议 4-6 周完成原型和基础开发，适合单门店试点。

包含：

- 用户查桌、查价、预约。
- 员工处理预约、开台、关台。
- 商家配置桌台、价格、活动。
- 客户基础信息沉淀。

### V1

建议在 MVP 验证后追加 3-5 周。

包含：

- 助教预约。
- 预约提醒。
- 活动规则增强。
- 客户标签。
- 基础看板。

### V2

建议在有真实门店数据后推进。

包含：

- 优惠券、会员卡、储值卡。
- 多门店。
- 收银、灯控、计时硬件集成。
- 财务对账。
- 自动化营销。

## 9. 验收标准

- 用户能在首页看到当前空桌数。
- 用户能查看桌台价格和助教价格。
- 用户能完成一次完整预约。
- 同一桌台同一时间段不能被重复预约。
- 员工开台后，用户端状态能同步变化。
- 员工关台后，桌台能变为空闲或清洁中。
- 商家能配置至少一种活动并在用户端展示。
- 商家能查看客户基础信息和预约记录。
- 私域触达必须区分服务通知和营销通知。

## 10. 不做范围

- 不做无限制营销群发。
- 不做复杂分销。
- 不做 AI 推荐。
- 不做复杂财务对账。
- 不在一期接入灯控、门禁、收银硬件。
