## 自动回流规则

```text
coordinator -> agent: instruction/fix
agent -> coordinator: handoff/status
coordinator -> read_thread(agent)   # 中枢主动拉取，不等待 agent 主动推送
coordinator -> next agent: instruction/fix/review
```

- Agent 完成任务后必须回传 `to_lane: coordinator`。
- 中枢读取回传后继续派发下一步，直到 QA 回归和验收官检核完成。
- QA/验收官发现普通问题时，中枢发 `fix` 给对应 Agent，修复后再次读取并复验。
- 只有需要真实外部信息、真实授权、高风险操作、重大业务决策，或验收官最终确认后，才暂停找用户。

## 中枢主动拉取调度器（强制）

本项目不再依赖固定 Agent “主动把结果推回中枢”。线程工具语义下，Agent 只能在自己的线程输出；因此中枢必须做 pull-based orchestration：

1. 中枢每次被用户消息或 heartbeat 唤醒，必须读取 `docs/agent-dispatch-state.md`。
2. 如果 state 里有 `active_request_id` 和 `expected_lane`，中枢必须优先 `read_thread(expected_lane)`。
3. 如果该线程最新 turn 已完成并包含 `message_type: handoff/status/review` 且 `to_lane: coordinator`，中枢必须：
   - 提取完成内容、改动文件、验证结果、剩余问题、下一步负责 agent、暂停条件。
   - 更新 `docs/agent-dispatch-state.md`。
   - 向用户输出阶段反馈。
   - 若未触发暂停条件，立即向下一位固定 Agent 投递任务。
4. 如果该线程最新 turn 已完成但没有标准回传，中枢必须立即投递 `message_type: fix` 要求补标准回传；不得让用户自己读线程。
5. 如果该线程仍在执行，中枢只记录等待，不派下一位，避免 QA/验收官基于未完成实现空转。
6. 如果没有 active request，中枢读取全部固定线程，寻找最新未处理回传；发现新回传则按第 3 步处理。
7. 每次中枢投递新任务后，必须把 `active_request_id`、`expected_lane`、`expected_thread_id`、`next_on_success`、`pause_conditions` 写入 `docs/agent-dispatch-state.md`。
8. 用户不需要也不应该自己打开子线程找结果；如果用户指出子线程已完成，中枢必须立即 `read_thread` 并补状态，不得解释后停住。

## 中枢调度状态机（强制）

每次中枢被用户消息或 5 分钟 heartbeat 唤醒时，不能只做状态汇报，必须按下面顺序执行一次调度动作：

1. 读取本文件“固定线程”表中的产品、后端、前端、QA、验收官主线线程；不得读取已归档、旧 fork 或重复线程。
2. 找到各线程最新的 `message_type: handoff/status/review/fix`，且必须是 `to_lane: coordinator` 的回传。
3. 如果最新回传没有触发暂停条件，并且写明“建议下一步负责 agent”，中枢必须立即向对应固定线程投递下一条 `instruction`、`fix` 或 `review`。
4. 如果 QA 或验收官结论为“不通过 / 不放行 / 失败”，中枢必须回派 `fix` 给对应实现 Agent；不得跳到下一阶段，不得找用户做最终验收。
5. 如果问题涉及部署、上传、写真实云数据库、初始化或迁移真实数据、账号密钥、删除/覆盖线上配置，中枢必须把状态置为 `blocked_user_auth`，只向用户说明需要哪项授权。
6. 对用户已经截图确认的运行时问题，只有本地静态检查或自动化测试通过不能关闭问题；必须有有效的微信开发者工具业务页面截图、用户手动复核结果或真实环境证据，才能进入验收官放行。
   - 微信开发者工具截图必须来自用户已手动打开并运行到真实小程序业务页的当前窗口；当前 MCP/CLI 自行新开或重开项目会停在欢迎页/空项目，不得作为验收截图来源。
   - 需要截图的 Agent 只能使用当前已打开窗口截图，并在报告中目检说明截图实际页面；欢迎页、空项目、文件编辑区、未编译页面、无业务内容模拟器一律判无效证据。
   - 如果当前窗口没有业务页，Agent 必须标记未实测或要求用户先手动切到目标页面；不得自己新开项目后把欢迎页当成页面验收。
7. 如果目标 Agent 超过一个 heartbeat 未回传，中枢只能发送一次收敛指令；再次无回传时标记为 `agent_stalled`，不得用自己的判断代替该 Agent 的回传。
8. 中枢最终对用户汇报时，必须区分：本地代码层、mock 层、微信开发者工具层、真实云端层、真机层；不得把低层级通过写成整体通过。
9. 中枢读到任一 Agent 的 `handoff/status/review` 后，必须先向用户输出阶段反馈：本轮执行 agent、完成内容、验证结果、剩余问题、下一步负责 agent；然后除非触发暂停条件，必须立即继续向下一位固定 Agent 投递任务，不得只总结不派发。
10. 只有以下情况允许“反馈后不继续派发”：需要用户真实授权、需要用户手动核验截图/真机、需要业务规则选择、需要高风险数据写入/删除/迁移、或验收官明确最终收口。
11. 同一用户可见缺陷如果连续两轮修复后仍未消失，中枢必须进入 `stop_coding_diagnose`：停止继续堆代码，先要求负责 Agent 输出真实数据流证据、失败层级、回档点和下一步最小动作；没有证据不得继续发实现任务。
12. 任何线上/云端修复前必须建立回档点：记录部署前云函数下载目录、部署时间、改动文件、数据写入前 before/after 或测试数据 ID；无法建立回档点时不得执行写库、迁移或覆盖线上配置。
13. 复利机制：每次出现“误判通过、错误归因、验证层级不足、重复修不好”的情况，中枢必须把错误记录到 `docs/复盘与回档机制-20260620.md` 或后续同类复盘文件，并在下一次派发中显式引用该教训作为禁止项。
14. 固定 Agent 完成任何任务后，最后一条消息必须是标准 `message_type: handoff/status/review`，且 `to_lane: coordinator`。不得只把结果写进文件、不得只发自然语言总结、不得让用户自己去线程里找结果。
15. 固定 Agent 回传后必须写明“下一步负责 agent”和“是否触发暂停条件”。如果缺少这两项，中枢必须发 `fix` 要求补齐，不得继续下一阶段。
16. 中枢读到固定 Agent 完成但未标准回传时，必须立即发一次“补标准回传”收敛指令；收敛后仍不回传，标记 `agent_handoff_noncompliant`，并向用户说明该 agent 未按规则回流。
17. 中枢每次派发任务时，必须同步更新 `docs/agent-dispatch-state.md`；每次读取回传后，必须将当前 request 标记为 `completed`、`blocked` 或派生新的 `active_request_id`。
